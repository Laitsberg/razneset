# Что разнесут?

Приложение для зрителей стрима «композитор разносит». Человек даёт ссылку
на свой плейлист в Spotify и видит два списка:

* **Уже разнесли**: его треки, которые есть в архиве стрима, с настоящей
  оценкой, номером стрима и датой;
* **Ещё не разнесли**: остальные треки с **прогнозом** оценки, от лучшего
  к худшему.

Архив тот же, что у сайта статистики [farymastats.info](https://farymastats.info)
(репозиторий `Laitsberg/faryma.stats`).

## Приложение

**https://laitsberg.github.io/razneset/** — открыть на телефоне, вставить
ссылку на публичный плейлист. Ставится на экран телефона: на Android —
кнопка «Установить на телефон» внизу (или меню Chrome → «Установить
приложение»), на iPhone — Safari → «Поделиться» → «На экран „Домой“».

* Ссылка запоминается. При каждом открытии сразу виден прошлый список,
  а свежий подтягивается в фоне — так новые треки появляются сами.
* Две вкладки: «Ещё не разнесли» — от лучшего прогноза к худшему,
  «Уже разнесли» — настоящая оценка, номер стрима и дата.
* Прогноз для незнакомого артиста нарисован пунктиром с пометкой
  «≈ новичок»: это просто среднее новичков, а не мнение об артисте.
* Строки — по 100, дальше «Показать ещё»: прокрутка в прокрутке на
  телефоне мучительна (знание из faryma.stats).
* Без сети открывается с прошлым списком (сервис-воркер `sw.js`).

Файлы: `index.html`, `app/` (стили и логика), `sw.js`,
`manifest.webmanifest`, `icons/` (`npm run icons` перерисовывает PNG из
`icons/icon.svg`). Прогноз считает тот же `lib/predict.mjs`, что
проверялся по истории.

## Как устроен прогноз

    прогноз = (сумма оценок артиста + K × приор) / (число его оценок + K),   K = 1

* **Приор** — средняя оценка **новичков**, то есть треков, чей артист попал
  в архив впервые. В таком положении и окажется трек незнакомого артиста.
  Новички получают чуть меньше остальных: 6,60 против 6,70.
* Если известен **жанр**, приор — среднее новичков этого жанра. Разброс
  большой: у классики 8,7, у джаза и блюза около 7,6, у хип-хопа и метала
  около 6,0. Жанр трека из Spotify пока брать неоткуда (см. «Чего нет»).
* У трека с несколькими артистами (feat.) их разносы складываются.
* Число переводится в ближайшую ступень шкалы. Шкала берётся с сайта
  статистики: в ней **26 ступеней**, а не 30. «Гениально+» и
  «кринж-контент-» в архиве не бывает: у крайних ступеней модификатор
  двигает оценку только внутрь шкалы.

**Почему K = 1.** `npm run backtest` идёт по эфирам по порядку и прогнозирует
каждый трек только по тому, что разнесли раньше. На двух отрезках по
80 эфиров лучшим вышло одно и то же K = 1:

| | ошибка, баллы | порядок (0 — никак, 1 — идеально) |
|---|---|---|
| всем ставить среднее | 1,39–1,42 | ≈ 0 |
| прогноз, артист уже был в архиве (≈ 52% треков) | 1,07–1,12 | 0,43–0,55 |
| прогноз, артиста не было | 1,50–1,51 | ≈ 0 |
| …то же, если жанр известен | 1,47–1,48 | 0,16–0,26 |

Ступени шкалы идут через 2 балла, модификатор двигает оценку на 0,3.
Значит, для знакомого артиста прогноз в среднем промахивается примерно
на полступени. Для незнакомого без жанра прогноз — просто среднее
новичков, и сортировать такие треки между собой он не умеет.

## Как сопоставляются треки

* **Артист.** Сначала по ID артиста в Spotify. Связку «ID → артист архива»
  строим по 1118 трекам архива, у которых в «Где» стоит ссылка на Spotify:
  так узнаются `祖堅 正慶` (Masayoshi Soken), `梶浦 由記` (Yuki Kajiura),
  `Korol i Shut` («Король и Шут»). Потом по имени без учёта регистра,
  диакритики и долгих гласных (`Kōji` = `Kouji` = `Koji`), кана переводится
  в ромадзи. Потом то же без учёта порядка слов (`Sawano Hiroyuki`).
* **«Уже разнесли».** По ссылке Spotify или по названию, но только если
  совпал и кто-то из артистов: одного названия мало, «Lemon» есть у многих.
  Скобки и хвосты версий («- Remastered 2011», «(TV Size)») не мешают.
  У названий на двух языках («悲しみがとまらない I CAN'T STOP THE LONELINESS»)
  есть второй ключ по латинской части.
* **Фильтры** для «ещё не разнесли»: короче 2:00 — убираем; минусовки,
  off vocal, караоке, фортепианные версии — убираем; дубли (ремастер,
  сингл и альбомная версия одной песни) — убираем; длиннее 6:00 —
  помечаем (за них доплата).

## Spotify: откуда берутся треки

Проверено 16.10.2026:

* Официальный Web API в Dev Mode с февраля 2026 **не отдаёт треки чужих
  плейлистов**, только своих и совместных.
* Embed-страница (`/embed/playlist/…`) отдаёт только **первые 100** треков.
* Внутренний запрос веб-плеера `fetchPlaylistContents` с анонимным токеном
  с embed-страницы отдаёт **все** треки: проверено на 1639 и на 10 000
  (предел Spotify), 10 000 — за 40 секунд.

Это **неофициальная** дорожка. Запрос опознаётся по отпечатку, который
меняется с обновлениями веб-плеера. `lib/spotify.mjs` ищет свежий
отпечаток в коде open.spotify.com сам, записанный остаётся запасным. Если
Spotify закроет анонимный доступ совсем, для всех, кроме пяти человек
со входом, останутся первые 100 треков через embed.

Закрытые плейлисты не читаются: в приложении нужна подсказка «сделай
публичным».

## Сервер

Railway, проект `razneset`, сервис `server`:
**https://server-production-ae29.up.railway.app**

| Адрес | Что отдаёт |
|---|---|
| `/playlist?url=<ссылка на плейлист>` | все треки публичного плейлиста: название, артисты с ID, длительность |
| `/health` | `{"ok":true}`, если сервер жив; в Spotify не ходит |
| `/status` | ходит в Spotify: есть ли токен и откуда взяты отпечатки запросов. `hashesFrom: "fallback"` — повод проверить: в коде плеера отпечатки не нашлись |

Прогноз сервер не считает: телефон берёт треки здесь, а модель — с GitHub
Pages, и считает сам. Так сервер остаётся крошечным, а лайки, полученные
через вход в Spotify (шаг 5), пойдут той же дорогой.

* Ответ хранится 5 минут: переоткрыть приложение можно без нового похода
  в Spotify, а свежедобавленный трек появится почти сразу.
* С одного адреса — не больше 20 новых плейлистов за 10 минут, чтобы
  никто не выжег анонимный доступ на всех. Уже загруженные отдаются и
  сверх этого.
* Ответ сжимается: 1639 треков — 112 КБ.
* Локальные файлы, которые человек добавил в плейлист со своего
  компьютера, в ответ не попадают: в Spotify их нет.

Скорость с Railway (16.10.2026): 1639 треков — 3,4 с, 10 000 — 15 с.

Сервер пересобирается сам при пуше в `main`, но только если поменялись
`lib/`, `server/`, `Dockerfile`, `railway.json` или `package.json`.
Обновления модели (`data/`) его не трогают.

## Обновление модели

Воркфлоу `.github/workflows/model.yml` каждые три часа берёт архив с
farymastats.info, прогоняет проверки, пересобирает `data/model.json` и
коммитит, только если архив изменился. Подстраиваться под время
обновления архива бесполезно: тот воркфлоу может идти больше часа.
Запустить руками: Actions → «Пересобрать модель прогноза» → Run workflow.

## Команды

    npm run model                       # собрать data/model.json (≈ 1 мин в первый раз)
    npm run backtest                    # проверка прогноза по истории
    npm run try -- <ссылка на плейлист> # посмотреть оба списка в терминале
    npm test                            # проверки без браузера (секунда)
    npm run test:app                    # приложение в браузере (нужен npm install)
    npm run shots                       # снимки экрана в трёх ширинах → shots/
    npm start                           # сервер на порту 3000 (или $PORT)

Приложению и серверу зависимостей не нужно, только Node 20+. Playwright
в `devDependencies` — для проверок и снимков. Код разбора архива (шкала,
«Артист — Трек», склейка имён, жанры) берётся с farymastats.info, а при
заданном `FARYMA_STATS_DIR` — из локальной копии `faryma.stats`.

## Чего нет и что дальше

* **Жанр для незнакомых артистов.** Spotify жанры больше не отдаёт.
  Кандидат — MusicBrainz: им сайт статистики уже пользуется для стран.
  Проверка показала, что с жанром сортировка новичков становится
  осмысленной (порядок 0,16–0,26 вместо 0).
* **Кандзи в именах.** Каны переводятся, кандзи нет. Артист с именем
  иероглифами узнаётся, только если он есть в связке по ID.
* `data/model.json` весит 1,3 МБ, 0,4 МБ в сжатом виде. Для телефона
  терпимо, но на шаге 3–4 стоит решить, считает ли список сервер или
  телефон.
